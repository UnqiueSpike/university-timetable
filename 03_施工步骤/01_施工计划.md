# 施工步骤

本计划将已有需求、架构和新版 UI 转化为可执行的开发步骤。按照现有技术栈推进，每完成一条业务流程，就同时检查页面、接口、权限和数据结果。

**设计基线：**新版 Figma 共 21 张桌面界面与状态图。本轮已接通认证、数据库、业务接口及同步；实际完成状态、测试证据和待大学验收事项以下方记录及交接文档为准。

**计划状态：**第一至第七步已完成本地实现和验证；客户同步时限、批准数据验收及大学部署仍待完成。勾选表示开发实现，不代表大学正式签收。部署与接管证据见 [交接记录](../app/docs/handoff.md)。

## 2. 技术分工

| 技术 | 在项目中负责什么 | 开始使用的阶段 |
| --- | --- | --- |
| Next.js + TypeScript | 页面、布局以及服务端应用代码 | 第一步 |
| Tailwind CSS + shadcn/ui | 按 Figma 实现样式和通用界面组件 | 第一步 |
| PostgreSQL | 保存身份关联和业务数据 | 第二步 |
| Drizzle ORM | 数据表定义、数据库迁移、查询和事务 | 第二步 |
| Better Auth | 登录、退出与会话管理 | 第三步 |
| tRPC | 业务查询和写入接口，连接页面与服务端业务逻辑 | 第三步建立基础，第四步接通课表 |
| Zero | 获授权数据的实时或近实时同步 | 第四步后进行小范围验证，第七步完整接入 |
| AWS + 待选定的 IaC 工具 | 试点部署、基础设施重建和运维 | 前期确认环境条件，第八步完成部署 |

业务写入暂按现有契约执行：页面 → tRPC → 业务层权限与参数检查 → Drizzle → PostgreSQL。Better Auth 负责认证，业务层负责判断具体数据能否读取或修改。

Zero 的订阅范围、身份传递及与 tRPC 查询的分工需要验证后记录；不能假定同步通道自动继承 tRPC 的权限检查。

| 5 | 完成教师维护和公告 | US-05、US-06 | 教师保存、审计记录、学生查询结果的完整流程 |

## 4. 第一步：建立工程与界面基础

**目标：**从文档仓库进入可运行的应用工程，先在浏览器看到新版登录页。

### 施工任务

- [x] 保留现有需求和设计目录，在仓库根目录新增 `app/`，作为完整 Next.js 项目的目录。
- [x] 初始化 Next.js、TypeScript，确定运行环境和包管理器，提交依赖锁定文件。
- [x] 配置 Tailwind CSS 和 shadcn/ui，按 Figma 建立颜色、字体、间距、圆角等基础样式。
- [x] 建立按钮、输入框及表单布局等当前需要的共用组件。
- [x] 实现新版静态登录页，补充窄屏布局；认证接入放在第三步。
- [x] 添加根目录 README，说明项目结构、环境要求、安装、启动和检查方式。
- [x] 添加忽略规则和不含真实密钥的环境变量示例。
- [x] 建立基本自动检查，包括类型检查、代码检查和正式构建。

建议应用内部结构如下，具体文件按实际需要逐步创建：

```text
app/                       # Next.js 项目根目录
  src/
    app/                   # 页面、布局及路由入口
    components/            # 通用界面组件
    server/
      auth/                # 认证配置和会话处理
      api/                 # tRPC 接口
      services/            # 业务规则和授权
      db/                  # Drizzle 数据表与数据库访问
      integrations/        # 外部数据适配
  public/                  # 页面静态资源
```

### 完成标准

另一位开发者拉取仓库后，能够按 README 安装依赖并启动应用；浏览器可打开新版登录页，基本检查和正式构建通过。此时只声明界面可运行，不声明登录功能完成。

## 5. 第二步：接通数据库与测试数据

**目标：**页面所需的数据有真实存储，开发环境可以重复建立。

### 施工任务

- [x] 建立本地 PostgreSQL 环境，配置服务端数据库连接。
- [x] 接入 Drizzle，建立迁移生成与执行流程。
- [x] 先落实课表所需实体：用户身份关联、科目、班级、课表条目、学生班级关系、数据来源及容量快照。
- [x] 与 Better Auth 的身份模型对齐用户标识和关联方式，避免创建相互独立的两套用户身份。
- [x] 将外键、唯一性、起止时间等已约定约束落实到数据库或服务端校验。
- [x] 准备至少两个学生和两组不同课程的数据，以及限定课程范围的教师测试身份；认证账户在第三步通过认证方案建立。
- [x] 准备容量未知、容量为零、无课程及失效班级关联等测试场景。
- [x] 将测试数据读取与转换放入数据接入适配器，区分测试来源和正式来源。
- [ ] 取得数据负责人批准的测试数据后验证 FR-01；当前合成数据只用于机制测试，尚无批准记录。
- [x] 定义重复导入、课程取消和班级关联失效的处理方式；区分完整快照、增量更新与数据源故障。

后续分享、公告和审计的数据表随对应阶段增加。落实 Supplement 与 Announcement 时同步补齐契约中的 `revision` 字段。

### 完成标准

空数据库可以通过迁移和测试数据脚本建立可用环境；重复导入不会重复创建相同外部记录；未知容量保留为 `null`，测试数据不会被标为已验证的正式数据。数据源故障不会被解释为删除所有课程。

本阶段实现与本地验证记录见[数据库说明](../app/docs/database.md)。认证账户仍在第三步建立；FR-01 批准数据源验收保持待办。

## 6. 第三步：完成登录与权限基础

**目标：**完成 US-01，让系统识别当前用户及其可操作范围。

### 施工任务

- [x] 接入 Better Auth，完成所需认证表及业务用户关联的迁移。
- [x] 连接登录表单，完成登录、退出、会话读取和会话失效处理。
- [x] 为本地开发建立可重复创建的测试账户，避免把测试凭据当成正式环境账户。
- [x] 根据会话和授予的权限展示学生或教师入口，不能通过界面自行选择并获得教师权限。
- [x] 建立 tRPC 基础、运行时参数校验和统一错误处理，实现 `account.me`。
- [x] 建立共用的服务端授权逻辑，区分操作权限、课程范围和本人数据范围。
- [x] 验证未登录访问、退出后的访问、学生访问教师接口及伪造用户标识等情况。

注册、找回密码及大学身份校验方式在接入时明确；不能仅因使用大学邮箱格式就认为身份已经核实。大学 SSO 按现有范围仍属于扩展，不作为基础登录开发的前置条件。

### 完成标准

学生和教师可以真实登录并进入对应界面；退出后受保护查询被拒绝；直接调用接口不能绕过身份或权限校验。兼具两种身份时按具体操作授权。

## 7. 第四步：完成个人课表和课程详情

**目标：**完成第一条端到端流程：登录 → 查询本人课表 → 查看课程详情、容量和来源。

### 施工任务

- [x] 按新版 UI 实现周课表、日期切换、课程卡片和详情抽屉。
- [x] 实现 `timetable.mine` 和 `timetable.getEntry`，从真实数据库读取数据。
- [x] 根据当前用户有效的 StudentClass 关系限制查询范围，不能接受客户端自行指定查询他人的身份。
- [x] 按契约处理时间区间、稳定分页和全部页面加载；统一按 Australia/Sydney 展示时间。
- [x] 展示课程时间、地点、类型、容量、来源和验证状态，并区分补充信息。
- [x] 实现加载、无课程、查询失败、容量未知及窄屏布局。
- [x] 自动验证学生之间的数据隔离、失效班级关系、时间区间边界、分页及容量空值。

### 完成标准

两个学生登录后分别看到自己的课程；修改数据库中的测试数据并重新查询后能看到对应结果；查询失败不会显示成空课表，未知名额不会显示为零。

### 此时提前验证 Zero 和部署条件

用一小组测试数据验证：通过当前写入路径保存后能否同步到授权客户端、不同用户能否正确隔离、权限撤销后是否移除可见数据、断线后是否重新认证。记录版本、接入方式、结果和未解决问题。

同时确认大学 AWS 环境、可用资源、访问方式及同步服务的部署条件，确定 IaC 工具。验证失败时先解决边界或记录候选替代方案的评估，不把未验证的同步路径当成既定实现。

本阶段应用验证见[课表说明](../app/docs/timetable.md)。Zero 小范围实验已通过写入同步、隔离、权限撤销及断线重认证；已发现会话失效后旧内存缓存仍在，完整集成须显式隐藏/销毁。IaC 选定 Terraform，大学 AWS 账户、区域、访问及资源仍待提供，部署验收保持未完成。详见[同步与部署验证](../experiments/zero/README.md)。

- [x] 实现公告草稿创建、编辑、发布、目标学生查看和撤回。

## 9. 第六步：完成分享、比较和撤销

**目标：**完成 US-04，创建和终止授权作为一个整体交付。

### 施工任务

- [x] 明确接收人的受控选择方式、分享字段、有效期及用户同意提示。
- [x] 将 Full Timetable / Availability Only 映射到服务端字段白名单。
- [x] 实现 `share.create`、`share.list`、`share.read`、`share.revoke` 和 `timetable.compare`。
- [x] 将分享列表、创建表单、成功提示和复制链接界面接入接口。
- [x] 实现比较空状态、有效比较和无效链接状态。
- [x] 实现撤销确认、撤销结果以及到期处理，每次读取和分页都重新检查授权。

## 12. 每完成一步如何记录

1. 将该阶段拆成具体任务，关联 US、FR、NFR 或 DEL 编号。
2. 完成对应实现、必要测试及演示，再勾选本文件中的任务。
3. 在[可追溯列表](../01_需求工程/03_可追溯列表.md)补充实际代码、提交或 PR、测试记录链接。
4. 如果业务范围或权限变化，更新[需求变更记录](../01_需求工程/04_需求变更记录.md)，同步相关模型、接口与原型说明。
5. 在阶段结束时记录已完成、未完成及下一步，避免把静态 UI、接口实现和验收完成混为同一状态。
6. 按用户 2026-09-19 的要求，每个施工阶段验证通过后单独提交到 Git，并推送到现有远程仓库；同步报告提交号和仍待验收的事项。

**当前进度：第一至第七步本地实现完成；第八步 Terraform 配置、运行手册和本地恢复演练完成，大学部署及独立接管验收待办。** 第二步的 FR-01 批准数据源验收仍待客户提供批准记录及数据；不能将合成测试通过等同于该项验收通过。
