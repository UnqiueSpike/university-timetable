Functional Requirement（功能需求）规定系统应具备哪些行为和能力；\
Non-functional Requirement（非功能需求）规定质量要求与约束，包括性能、安全、可靠性和可访问性等。两者共同明确：**系统要做什么，以及在什么条件下达到什么要求。**

## Functional Requirement（功能需求）

- **身份认证与权限：**支持学生和教职员工登录，并根据角色控制信息的查看和修改权限。
- **课程表查看：**学生能够查看个人课程表，包括课程时间、地点、类型和科目。
- **班级容量：**在有合适数据的情况下，显示班级容量或可用名额。
- **数据来源与验证状态：**展示数据来源或验证状态，区分经过验证的课程表数据与补充信息。
- **课程表分享与比较：**学生能够在同意并授权的情况下，与同学分享和比较课程表。
- **教职员工管理：**提供 Dashboard，支持教职员工查看相关课程和课程表记录，修改经过批准的信息。
- **公告管理：**支持公告的创建、编辑、发布和撤回，并定向发送给特定课程或用户群体；学生能够查看相关公告。
- **修改审计：**记录教职员工修改行为的基本审计信息。
- **数据接入：**接入一种经过批准的正式数据源、数据集、Mock API 或测试数据。
- **更新同步：**将课程表信息和公告的更新同步到学生端及教职员工端。

## Non-functional Requirement（非功能需求）

- **性能与及时性：**在约定的使用条件下，满足页面响应和更新同步要求；具体性能指标及更新时限由双方确认。
- **安全与隐私：**防止未经授权的数据访问和修改，保护课程表分享中的学生隐私，并尽量减少个人信息的收集和存储。
- **可靠性：**提供清晰的监控、恢复和维护要求，支持故障后的系统恢复。
- **易用性与兼容性：**界面清晰，能够在受支持的现代 Web 浏览器中运行，并适配桌面端和移动端。
- **可访问性：**开展无障碍测试，并满足大学确认的相关标准。
- **可部署性：**能够部署到大学控制的 AWS 或 Azure 基础设施，并使用 Infrastructure as Code 重建环境。
- **可维护性：**应用与官方课程表数据源解耦，采用大学能够维护和支持的技术，提供清晰的架构、数据模型及技术决策文档。
- **可测试性：**关键业务流程由自动化测试覆盖，并开展功能、可用性、性能、无障碍和安全评估。
- **运行独立性：**避免强制依赖付费 SaaS 产品或厂商托管的运行时服务。
- **可移交性：**提供部署、回滚、配置、密钥管理、运维及用户文档，使大学内部团队能够接管系统，并明确已知限制和生产就绪差距。
