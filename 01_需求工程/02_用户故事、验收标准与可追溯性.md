# 用户故事、验收标准与可追溯性

**用户视角：**User Story（用户故事）用“谁、想做什么、为什么”表达用户目标与价值。它帮助团队理解功能存在的理由，但通常还不足以直接指导实现，需要进一步明确业务规则、边界和异常情况。

**验收依据：**Acceptance Criteria（验收标准）把用户故事细化为可以检查的完成条件，使开发和测试有共同依据。核心是**把模糊期望变成可验证的约定**：开发者知道要实现什么，测试人员知道如何检查，需求方知道依据什么验收。

## 用户故事与验收标准

以下为核心功能的初稿；具体权限、分享规则及同步时限需与客户确认。

### US-01 登录与权限

**用户故事：**作为学生或教职员工，我希望通过身份认证访问系统，以便安全地使用获授权的功能。

**验收标准：**

- 有效身份能够登录，并访问其角色允许的功能。
- 未登录用户不能访问受保护的数据。
- 用户不能通过直接访问页面或接口读取、修改未获授权的数据。

### US-02 查看个人课程表

**用户故事：**作为学生，我希望查看个人课程表及课程详情，以便安排学习和出行。

**验收标准：**

- 显示与当前学生对应的课程表，包含时间、地点、课程类型和科目。
- 没有课程记录时显示明确的空状态；加载失败时显示错误提示，不误示为没有课程。
- 桌面端和移动端均能查看课程信息。

### US-03 查看容量与数据可信度

**用户故事：**作为学生，我希望了解班级容量及信息来源，以便判断名额情况和信息是否可信。

**验收标准：**

- 有合适数据时，按确认的定义展示班级容量或可用名额。
- 无容量数据时显示暂无数据，不将未知名额显示为零。
- 展示来源或验证状态，并区分经过验证的数据、补充信息和测试数据。

### US-04 分享与比较课程表

**用户故事：**作为学生，我希望自主选择与同学分享并比较课程表，以便协调共同安排。

**验收标准：**

- 分享前取得学生同意，并明确分享内容和接收范围。
- 接收者只能查看获准分享的信息；未获授权的访问被拒绝。
- 比较视图正确呈现本人及获准查看的同学课程安排。

### US-05 维护批准的信息

**用户故事：**作为获得授权的教职员工，我希望查看相关课程并维护批准的信息，以便让学生获取准确的更新。

**验收标准：**

- Dashboard 仅显示其授权范围内的课程和课程表记录。
- 允许修改批准的字段，拒绝超出权限的修改。
- 保存成功后可以查看更新结果，并留下基本审计信息。
- 保存失败时明确提示，不显示为修改成功。

### US-06 发布与查看公告

**用户故事：**作为教职员工，我希望向指定课程或用户群体发布公告，以便相关学生获知课程表变更。

**验收标准：**

- 授权教职员工能够创建、编辑、发布和撤回公告。
- 已发布公告对目标学生可见，未发布公告不作为正式公告展示。
- 撤回后，公告不再作为有效公告展示。
- 公告的管理和访问遵守确认的权限及目标范围。

### US-07 获取同步更新

**用户故事：**作为学生或教职员工，我希望及时看到课程表和公告的最新状态，以便减少信息不同步造成的误解。

**验收标准：**

- 更新成功后，相关用户界面在双方约定的时限内显示最新有效状态。
- 同步仍遵守访问权限，不向无权用户传递受保护内容。
- 同步失败时提示状态，恢复后能够重新获取更新。

## 可追溯性

为每个重要需求分配唯一 ID，并在 Issue、Figma、代码、PR 和测试中互相引用。现有用户故事沿用 US-01 至 US-07；新增故事顺序编号，已有 ID 不重复使用或随意更改。

**规则：需求 → 设计 → 实现 → 测试必须可双向追踪。**

例如：

> US-01 ↔ Figma 页面 ↔ GitHub Issue ↔ PR/Commit ↔ Test Case

- 在需求对应的 Issue 中汇总 Figma、实现 PR/Commit 和测试用例链接。
- 在 Figma、相关代码注释、PR 和测试用例中注明需求 ID，并引用对应 Issue。
- 当需求变化时，根据这些关联检查所有受影响的设计、代码和测试，并同步更新。

以上为后续工作规则，相关设计、实现和测试产生后补充实际链接。
